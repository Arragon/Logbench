# R6-039 · 多文件并行与有序归并

## 交付

| 文件 | 职责 |
| --- | --- |
| `src/shared/ordered-reducer.js` | 页面侧有序归并（`window.LBOrderedReducer`） |
| `server/indexing/ordered.py` | 服务端同一语义的镜像 |
| `server/indexing/parallel.py` | 文件级并行 + 记录局部计算的 lane 扇出与按序提交 |
| `tools/r6_load.py` | 可配置负载命令：同时报告吞吐与查询 p95 |
| `tests/r6/ordered-reducer.test.cjs` / `tests/test_r6_parallel_pipeline.py` | 见下 |

### 语义（两侧一致）

- `seq < next_seq` → `stale`（已提交，不重复提交）
- 已在缓冲 → `duplicate`
- `token` 小于当前 fencing → `old_token`
- `seq == next_seq` → 提交并连带排空连续后继
- 否则进缓冲，超过 `max_buffer` → `reducer_overflow`；缓冲过半即 `pressure`，
  生产端据此背压，而不是等缓冲满了再补救
- checkpoint 只跟随连续已提交批次

### 为什么不能按字节切

记录边界不是字节边界。文件级并行 + 单文件顺序分帧，巨型 Traceback 跨块仍然完整；
`test_a_traceback_spanning_many_blocks_stays_whole` 用 8000+ 行、>192 KiB 的单条
Traceback 在 64 KiB 块下验证：仍是 1 条记录，`lines` 跨度等于源文件行数。

## 验收命令

```
env -u PYTHONPATH ~/.local/bin/python3.9 -m unittest tests.test_r6_parallel_pipeline -v   # 9 项
node --test tests/r6/ordered-reducer.test.cjs                                              # 8 项
env -u PYTHONPATH ~/.local/bin/python3.9 tools/r6_load.py \
  --files tests/fixtures/r6/golden/edge_cases.log \
  --files tests/fixtures/r6/golden/traceback_chain.log --lanes 1,2,4 --out qa/evidence/M3-load.json
```

### worker 数不改输出

`test_worker_counts_one_two_four_six_eight_agree`：lane 数 1/2/4/6/8 与顺序构建的
规则层摘要**完全相同**（8 组摘要去重后只剩 1 个值），且提交后 ordinal 严格递增。

### 跨语言差分

`test_python_and_javascript_agree_on_every_schedule`：同一批提交顺序（含乱序、
重复、缺口）分别喂给 Python 与 Node 的归并器，提交轨迹逐项相等。两边实现漂移会
直接让这个用例变红。

### 负载与查询并发

`qa/evidence/M3-load.json`（2 个夹具文件，lane 1/2/4）：三种并行的内容摘要一致
（`digest_stable: true`），查询 p95 0.19–0.22 ms，无查询错误。夹具过小，吞吐数字
不具代表性；1 GiB 的吞吐/内存见 `qa/evidence/M3-gate.md` 的 `cold_warm` 用例。

## 已知限制

- `parse_slots` 默认 4（符合票据「解析槽初始 4」），6/8 只作为测量档位，未作为默认。
- 记录局部计算扇出后仍受 Node 池 worker 数限制；lane 数大于 worker 数时排队而非
  提速，这一点在 `worker_stats` 里可见。
