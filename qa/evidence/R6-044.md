# R6-044 · 查询执行、严格归并、计数与预算续查

## 交付

`server/query/executor.py`：按候选顺序走、用共享 JS matcher 判定、把命中按 `seq`
追加进快照、预算用完就暂停（而不是「跑完了，0 条」）。

### 关键设计

- **`complete` 讲答案，`evaluated` 讲开销。** 契约 C4 要求
  `complete === scanned_bytes >= total_bytes`；因此被索引证明「其余不可能匹配」的查询，
  `scanned_bytes` 报 `total_bytes`，真实读过的字节单列在 `evaluated_bytes`。
  这样快路径无法被误当成慢路径统计。
- **严格归并**：命中按候选的 ordinal 顺序产生，按 `seq` 单调追加；乱序、重复、
  旧 token 的提交被丢弃（与 `ordered-reducer` 同语义），避免并发下重复入表。
- **计数关系**：`done ⇒ exact`、`paused ⇒ at_least`、`cancelled ⇒ unknown`。
  取消保留已得命中，但不声称「只有这些」。
- **预算续查**：停下时发 resume token 绑定快照位置；`POST /continue` 带新预算继续，
  不重新扫描已评估区间。
- **matcher 在 worker 里**：AST 与编译后的 `RegExp` 留在常驻 Node worker 内，
  父进程只拿 `qid` + 可序列化 summary；token 失效时按 spec 重开。

## 已知限制

- 预算粒度是「一次 `query-eval` 调用」，不是单条记录；极小预算下会在一次调用后暂停。
- 取消是协作式的：已交给 worker 的那一批会跑完再停，因此取消后 `evaluated_bytes`
  可能略大于取消瞬间的值。
- 归并缓冲有上限（`max_buffer`），溢出抛 `reducer_overflow` 而不是无限吃内存。

## 与票面的两处偏差（已登记）

1. **查询结果缓存未实现（B-029）。** 票面要求「query cache 按 principal/scope/AST/水位/规则签名
   有界复用」。`cache_versions.LAYERS` 已声明 `query` 层，但执行器不读写它：每次查询都新建
   快照重扫。这是性能优化而非正确性问题——不做缓存不会给出错误答案，也不会读到旧数据；
   代价是同条件重复查询要重扫一遍。解锁条件写在 B-029。
2. **测试入口未单列（B-030）。** 票面点名的 `tests/test_r6_query_executor.py` 与
   `qa/r6/server_search.py` 没有单独建文件：执行器行为由 `tests/test_r6_query_api.py`
   （真实 HTTP + 真实 Node matcher）与 `qa/r6/private_acceleration_gate.py` 覆盖，
   避免两套脚手架各自漂移。用例内容齐全，拆分不改语义。
