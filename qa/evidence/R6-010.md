## 语义决策（都写成断言）

| 规则 | 理由 |
|---|---|
| 只有 `The above exception was the direct cause…` / `During handling…` 才产生链 | 相邻两段堆栈默认是**两次独立失败**，不是因果链 |
| 标记之后再出现 `Traceback` 头，继续同一个 trace | 否则一条因果链会被切成两条，`primary_type` 丢失 |
| 无终止异常 → `truncated=true`、`reason=no-terminal-exception` | 截断不能被当成"没有错误" |
| 帧内源码行标 `source_from_log=true` | 日志里的 `raise X` 不等于文件真内容 |
| 前缀输出（`| Traceback`、`+ Exception Group`）解析结果与无前缀一致 | 按行加戳的输出非常常见 |
| `ExceptionGroup` 只标记、不展开 | 树形展开属于后续视图，不是分帧职责 |
| 非 Python 堆栈（Java/Go/JS）标 `non_python` 并停止半解析 | 半解析比不解析更容易误导 |
| 行跨度按记录内相对行号给出 | 详情抽屉要能指回原文 |

## 一处实现过程中的真实修正

`stripPrefix` 最初只剥离"行首一两个前缀字符"，遇到 `  |   File "a.py"…`（先缩进再竖线）就失配，`ExceptionGroup` 的帧读成 0 条。改为**循环剥离"缩进 + 单个 `|`/`+`"** 后修复。这类嵌套前缀在并发进程日志里很常见。

## 与分帧器的分工

`framer` 决定"一条记录到哪里结束"，`traceback` 只决定"记录内部的因果结构"。二者都不做字段提取（`R6-011`/`R6-012` 负责），避免三个模块各自解释同一段文本。

## 未覆盖

- 超长堆栈的 `raw ref`（用字节区间代替全文）未做，属 `R6-014` 的存储层职责。
