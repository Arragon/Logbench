## 一处必须记录的真实缺陷（已修）

`release()` 最初**删除**租约记录，导致下一次 `acquire()` 从 `fencing=1` 重新计数——旧持有者的 token 会与新持有者**撞号**，fencing 的保护当场失效。首个双页测试直接暴露（B 接手后拿到 `fencing=1`，A 的旧 token 被当成新 token）。

修复：释放时保留记录，写入 `released=true, expires_at=0, owner=null`，使计数单调递增。修复后 A(fencing=1) → B(2) → A(3) → B(4)，旧 token 全部 `stale_fencing`。

## 实测要点

- 两页竞抢只有一个写者：B 得 `lease_held`。
- 旧 token 的提交与续租都被拒（`stale_fencing`），且**旧写入没有落地**（payload 仍是 A 的值）。
- 新持有者提交生效（payload 变为 B 的值）。
- TTL 过期后可被接管，fencing 继续递增。
- 删除 `window.BroadcastChannel` 后仍能正确获取租约（`fencing=5`）：正确性不依赖通知通道。
- 全程 `isSecureContext=false`，不依赖 Web Locks。
