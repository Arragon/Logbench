# R6-036 · 流式索引流水线

## 交付

- `server/indexing/pipeline.py`：4 MiB 块读 → Node 分帧/规则 → `commit_batch`
  （记录与 checkpoint 同事务）→ 推进 watermark。
- 续跑语义：checkpoint 里同时保存**分帧器状态**（position、pending 字节、
  ordinal、open record），重启后由 `restore` 命令回放，因此「进程在块中间死掉」
  既不丢也不重。
- 代次冲突：读取前后各校验一次 `content_signature`；大小变化、读取期间被改写、
  读取期间被截断，全部 `generation_conflict`，已提交的旧代次保留并标记
  `superseded`。

## 验收命令

```
env -u PYTHONPATH ~/.local/bin/python3.9 -m unittest tests.test_r6_index_pipeline -v
```

10 项全绿，关键断言：

- `test_resume_after_a_crash_neither_loses_nor_duplicates`：中断后继续，
  `restarted_from` 等于上次 `bytes`，且逐条 `(ordinal, lines, message)` 与
  干净全量运行**完全一致**（不只是条数相等）。
- `test_a_file_rewritten_during_the_run_is_a_generation_conflict` /
  `…truncated_during_the_run…`：用 `on_progress` 在运行中真实改写/截断文件，
  两条路径都抛 `generation_conflict`。
- `test_a_truncated_file_does_not_resume_from_the_stale_checkpoint`：文件变短 →
  新代次、`restarted_from == 0`，不复用末段已经越界的 checkpoint。

## 备注

修复过的真缺陷：原实现每批新建分帧器、靠「对齐到下一行」续跑，导致 resumed
索引只有 2 条记录（干净运行 6 条）。根因是 ordinal 从 1 重新开始、且块尾的
半行被当成完整记录。现在分帧状态与批次同事务落盘，并按块尾的字节边界续读。

## 块大小的取舍（实测）

分帧器不能回退到块内某个位置，所以一旦一个块产生的记录数超过回包上限，父进程只能
用同一块再问一次。1 MiB 块 + 10k 记录上限让普通日志「一块一回包」，实测把
16 MiB 的线上数据量从 577 MB 降到 112 MB（请求数 163 → 38），并顺带把块尾残片
留在内存里，不再重新 `read`（`carry`）。这不是微优化：冷索引的瓶颈是每条记录的
JSON 编解码与 SQLite 写入，重复发送同一块会把它放大成数量级。
