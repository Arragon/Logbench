# R6-082 · 解析缓存与重建管理

## 交付

| 文件 | 职责 |
| --- | --- |
| `server/indexing/cache_api.py` | `GET /api/v2/cache`（分页、按层/状态筛选、汇总）、`POST /api/v2/cache/rebuild`、`POST /api/v2/cache/purge` |
| `src/ui/cache-manager.js` | 文件表（三层状态徽标 + 版本 + 大小 + 引用）、展开依据、批量选择影响范围、重建/清理确认对话框 |
| `tests/test_r6_cache_api.py` | 9 项：层状态、清理白名单、原文不可清、引用保护、404、审计 |
| `qa/r6/cache_manager.py` | 真实 API + 真实页面，23 项 |

### 关键语义

- **`raw` 不是缓存。** 它是唯一不可重建的层，因此既不出现在 `purgeable` 里，`purge` 传 `raw` 也直接 400 `raw_not_purgeable`。原文是用户的数据，不是我们的中间产物。
- **清理删指针，不删字节。** `purge` 走 `registry.invalidate()`，只让派生层指针失效；存在活动引用（pin）时旧版本保留到引用过期，阅读不会中断，返回体 `rawKept: true` 并给出 `pinned` 清单。
- **重建就是索引任务，不是同步请求。** `rebuild` 创建与 index API 同一个 job，进度落到任务面板已经在读的 checkpoint。`layers` 里不含 `structure` 时复用结构层——这才是"只重算规则层"能成立的原因。
- **状态不臆造。** 没有指针且没有尝试记录 = `pending`，不是 `complete`；失败的尝试保留错误码，页面显示 `失败: coverage_mismatch` 而不是一行绿的零记录。旧版本还在但新尝试失败 → `stale`（可读但过期）。
- **筛选在服务端做。** `layer`/`state` 在内存里过滤当前页并重算 `summary.byState`，避免"客户端过滤当前页"造成计数和实际不符。

## 已知限制

- 清理只在**单文件**粒度确认；没有"整个存储根批量清理"，因为批量误删派生层仍需逐个复核（B-047）。
- 没有"缓存占用趋势"与按大小排序的容量视图；当前只报单分片字节数。
- 引用（pin）只有过期时间，没有"谁在用"的可读标签，`pinned` 里是 token 与 owner id。
- 重建不提供进度百分比，只有任务状态；进度仍在任务面板看。
- 未在目标机（Linux 双路 E5、HDD 数据盘）复跑清理后的首查延迟，见 B-050。
