## 关键设计

1. **`matches()` 只返回扁平的四个字段**（`hit/mask/terms/skipped`）。它不为每条记录生成"通过对象"或高亮范围——R5 的 1.6 s 里大半花在把 13 万条记录连内容一起搬给 Worker。测试用 `Object.keys` 直接锁死这个形状。
2. **高亮是独立调用**：`computeMarks()` 只对真正渲染的行走，且默认 500 段上限。
3. **非法模式与空匹配模式都变成结构化错误**（`invalid_regex` / `empty_match`），`.*`、`a*`、`^` 在编译期就被拒，不可能进渲染循环造成死循环。
4. **投影版本显式**：`v1` = message + body（与 R5 一致）；`v2` 追加字段值、logger、fn、src。测试证明同一查询在两种投影下命中不同——这就是"保存视角"必须记录 `projection_version` 的原因。
5. **通配符保持字面量**：`%`、`_`、`.` 只在用户显式开正则时才有语义，避免意外继承 SQL LIKE / FTS 语法。

## 边界用例（均已断言）

- Unicode 大小写（`ÜBER` ↔ `über`）；非 BMP 字符（😀）的区间按 UTF-16 码元给出，`slice` 结果正确。
- 整词边界用 `[\p{L}\p{N}_]`：`foo` 不匹配 `foo_bar` 里的 `foo`。
- **CJK 例外**：中文没有词分隔符，`whole_word` 对含 CJK 的词退化为子串匹配（否则"中文"在"这是中文日志"里永远搜不到）。这是刻意的产品语义，已写成用例。
- `.` 不跨行；显式 `\n` 可以跨行。
- 空查询被拒绝（不匹配一切）；纯空格被视为有效搜索词。

## 130k 条匹配实测（Node，20 MiB 单文件）

```text
records 130,359
literal "energy"     18.3 ms   命中 18,740
zero-hit             11.5 ms   命中 0
regex "energy|floor"  7.0 ms   命中 18,740
单行高亮             0.064 ms
```

对照 R5 浏览器内同语料搜索 1,643–1,757 ms：**差距不在正则引擎，而在"是否克隆全部记录"**。字面量路径因为要对整段 haystack 做 `toLowerCase`，反而比 `iu` 正则慢——这说明"ASCII 快路"只在纯 ASCII 文本上才值得启用（实现里就是这么限定的）。

> 以上是 Node 同机数据，**不作为浏览器结论**；页面接入后由 `R6-011`/`R6-018` 用 `qa/r6/search_baseline.py` 复测。
