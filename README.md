# LogBench 3.0.3 · R5 独立部署版 · Python 3.9.11 兼容

前端沿用 LogBench R5 的界面、Traceback 卡片、时间线、字段/异常/节点规则编辑器、虚拟列表、时间筛选和多文件时间对比；服务端提供真实 IP 权限、共享日志库、规则版本、目录绑定、回收站、审计与覆盖式更新。

**运行依赖：Python 3.9.11+（带标准库 sqlite3）和现代 Chrome/Edge/Firefox。无需 pip、npm、Node、CDN 或独立数据库。** Node/Playwright 只用于可选开发测试，不参与部署。建议使用你们组织仍在维护的 Python 版本；本次实际服务测试使用 Python 3.13.5/Linux，另执行 3.9 语法与 API 边界回归；受环境下载限制，尚未用原生 3.9.11 解释器运行。详见 `docs/PYTHON39.md`。

> **已有 3.0.0 部署：** 首次迁移到 Python 3.9.11 兼容版本时必须停服并替换 `run.py`，再用目标 Python 启动。已有 v3.0.1 的 `run.py` 可以保留。旧版批量更新工具不会复制新的 `change-port.bat` / `.sh`、`tools/set_port.py` 或配置示例；如需快捷脚本，请从本包手工复制这些文件。**保留原有 `data/`、`var/`、`config.json`**，数据库无需迁移；有旧端口配置时，需另行设置 `50004`。
>
> Python 3.9 已于 2025-10-31 结束上游维护。本兼容包服务于已有的受控内网环境，不修复旧解释器自身的安全问题。官方依据见 `docs/PYTHON39.md`。


> **v3.0.3 页面修正：** 双击日志记录后的“记录详情”由挤占工作区的右侧 Flex 子栏改为悬浮抽屉。日志表格、左侧时间线尺寸保持不变，打开、关闭及切换详情不会主动改变日志记录的屏幕定位。只调整 `src/style.css`、`src/app.js` 和 `server/app.py` 版本号；服务接口、SQLite 和数据格式不变。运行中的 v3.0.2 可直接使用本文档的批量覆盖更新，无需改端口，也无需改 `config.json`。

## 一、直接运行

解压后进入 `LogBench` 目录。

```bash
# 只需首次执行：显式登记本机 IP 为管理员，初始化数据库后退出。
python run.py --admin-ip 127.0.0.1 --init-only

# 启动前后端，默认开启覆盖更新。
python run.py
```

浏览器访问 `http://127.0.0.1:50004/`。Windows 可用 `py -3` 代替 `python`，或运行 `start.bat`；Linux/macOS 可用 `python3` 或 `sh start.sh`。不自动将本机、回环地址或首次访问者升级为管理员。

如需明确指定 Python 3.9，Windows 使用 `py -3.9 -B run.py`，Linux/macOS 使用 `python3.9 -B run.py`；也可用随包的 `start-py39.bat` / `start-py39.sh`。先用相应命令的 `--version` 确认实际解释器。热更新工作进程和预检会继承同一个解释器，不会自动切换到更高版本。

初始日志库为空。使用右上角“打开日志”导入本机文件，文件只进入当前身份的浏览器缓存；或者把 UTF-8 日志按文件夹放入部署目录的 `data/`，在文件库点击“刷新目录”。`examples/` 是可选合成样例，不会自动放入日志库或冒充真实数据。

```text
LogBench/
  run.py                  稳定启动器/热更新监控
  worker.py               服务工作进程入口与预检
  src/                    R5 前端源码，无构建步骤
  server/                 HTTP/API/SQLite/身份/文件服务
  rules/                  首次初始化规则种子
  examples/               明确标记的合成日志
  tools/                  批量更新、服务端备份、set_port.py
  change-port.bat / .sh   交互修改持久端口
  config.example.json     配置示例，不直接覆盖现有 config.json
  data/                   运行后创建：共享日志库
  var/                    运行后创建：数据库、密钥、更新快照
```

`data/` 与 `var/` 不在交付包中预置用户数据，由服务自动创建。


### 快捷修改监听端口

**默认端口是 `50004`**。提供两种方式，均不需要修改程序源码：

**临时指定（本次运行生效）**：

```bash
python run.py --port 50005
# Windows + Python 3.9：py -3.9 -B run.py --port 50005
# Linux + Python 3.9：python3.9 -B run.py --port 50005
```

**永久修改（推荐）**：Windows 直接双击 `change-port.bat`，输入新端口；Linux/macOS 执行 `sh change-port.sh 50005`，或跨平台运行：

```bash
python tools/set_port.py 50005
```

以上命令只修改/创建部署根目录的 `config.json`，保留已有的 `host`、`data_dir`、`allowed_hosts`、权限设置和其他配置。若先前已经部署 v3.0.1 并在 `config.json` 中设置 `8765`，**它将覆盖新版默认端口**，需要运行一次 `change-port` 或手工改为 `50004`。`--port` 在命令行指定时优先级更高，不会写入 `config.json`。

**修改持久端口后必须重启正在运行的 LogBench。** 监控器不会热加载 `config.json`，也不要同时用两个启动器绑定同一份 `var/`。如使用 Nginx、Docker、系统防火墙或外部 `public_origin`，同步检查它们的代理目标、端口映射和浏览器访问地址。更换 Origin（协议、主机或端口）可能使浏览器的 IndexedDB 设置/文件缓存位于新的存储空间；请事先在旧地址导出完整工作区备份，切换后再恢复。本地服务端 `data/` 和 `var/` 不受此操作影响。

## 二、部署到内网服务器

将 `config.example.json` 复制为 `config.json`，根据实际机器修改。例如服务器 IP 为 `192.168.1.20`：

```json
{
  "host": "0.0.0.0",
  "port": 50004,
  "data_dir": "data",
  "state_dir": "var",
  "allowed_hosts": ["192.168.1.20", "localhost", "127.0.0.1"],
  "trusted_proxies": [],
  "public_origin": "",
  "max_connections": 32
}
```

管理员的 IP 填浏览器所在电脑的 IP，例如 `192.168.1.50`，不是服务器 IP：

```bash
python run.py --admin-ip 192.168.1.50 --init-only
python run.py
```

其他电脑访问 `http://192.168.1.20:50004/`。允许必要的入站端口，不要无差别关闭防火墙。配置相对路径相对于部署根目录。修改监听地址、端口、代理或 `config.json` 后需重启启动器。`--admin-ip` 是显式的运维授权动作，不应写进日常启动脚本反复执行。

**安全范围：可信内网。IP 识别不是登录强认证；同一 NAT/代理出口 IP 会被视为同一身份。** 未登记用户为只读访客，可以读取共享日志；不应把包含不同访问密级的数据放入同一个共享库。需要阻止一个 IP 时用“停用”，删除登记只会将其变回访客。公网请另配强认证网关，不要直接暴露本服务。

HTTPS、Nginx、systemd 和可选 Docker 示例见 `deploy/README.md`。

## 三、真实功能与数据归属

| 功能 | 行为 |
|---|---|
| R5 阅读界面 | 保留字段色彩、列显隐、完整 Traceback、来源跳转、多行折叠、实际命中规则证据、时间线分页和点位外观。 |
| 文件库 | 服务器层级目录、搜索、分页元数据、按需读取、下载；管理员可建目录、删除/恢复文件与目录。 |
| 本机文件 | 导入不上传，无隐式日志上传接口；正文使用 IndexedDB，个人设置/草稿/视角按身份隔离。 |
| 共享规则 | 管理员创建/复制/修改/软删除/恢复；每次写入检查修订号，冲突保留个人草稿。 |
| 规则绑定 | 个人单文件 → 个人最近目录 → 共享单文件 → 共享最近目录 → 服务端默认。目录操作明确“仅我 / 所有用户”。 |
| 规则试跑 | 真正执行 R5 Worker，不提交共享规则，不改原始日志；异常正则/超时保留旧结果。 |
| 时间筛选与对比 | 选择实际本机/服务器文件，完整小数秒排序、全局范围、2–4 文件共同时间轴、同步滚动、保存视角。 |
| 用户管理 | 管理员登记 IP、姓名、成员/管理员角色与停用状态；服务端逐请求授权，不靠隐藏按钮控制。 |
| 后台审计 | 记录共享文件、规则、权限及绑定变更；管理页面显示最近记录，API 可分页。 |
| 版本更新 | 默认监视应用源码，稳定后快照预检、替换服务进程、健康检查，启动失败回退旧代码。 |

共享规则删除前必须解除相关绑定，避免其他用户的文件突然落到不明默认规则。只修改显示规则/自定义点位不会改写日志原始等级。高级自定义规则依旧针对已支持的方括号头部，不代表任意日志语法都已自动识别；新增头部格式需补充解析适配。

### MCChecker 用户复用

独立启动后，在“管理后台 → 身份来源”填写 MCChecker **服务器部署目录**，可以预检、保存并启用。若它使用外置 data 目录，可填写自定义 data 路径。只读 `ip_mapping.json` 与 `admin_users.json`，不会导入 Python 模块、执行其代码或写回任何文件。外部模式下用户表只读；共享规则/文件权限由外部管理员身份决定，不会把 LogBench 本地管理员偷偷叠加进去。

切换前会检查当前访问 IP 在目标来源中仍为管理员。文件损坏/路径不可读时明确报错，不回退成匿名管理员。

运维误配置后的恢复（在服务器终端执行）：

```bash
python run.py --local-identity --admin-ip 192.168.1.50 --init-only
```

这会显式切回本地身份。外部人员 JSON 结构兼容基于 MCChecker 提交 `429dafaa4938ee42f59807b1720e56c225d8cbfa` 验证；你实际目录中的特殊格式仍须预检。

## 四、覆盖文件热更新

启动必须使用 **`python run.py`**，默认开启，不必安装 watchdog。支持覆盖：

```text
src/       前端 JS、CSS、HTML
server/    后端 Python
rules/     内置初始化规则文件
worker.py  工作进程入口
```

文件内容稳定约 1.5 秒后，启动器创建不可变发布快照，运行 Python 编译/导入/API 与资源预检；随后有序停止旧进程，启动新进程并检查健康。预检失败保留旧进程，启动失败自动回退旧快照；日志会打印 `[update] rejected`、`active` 或 `rolling back`。前端不会强迫刷新，版本提示允许先保存草稿再刷新。

**这属于受控自动重启，不是零停机或进程内模块替换。** 切换可能短暂断开请求；失败的写操作不会自动重试，用户确认后再提交。读取任务仍在客户端的已加载日志可继续阅读。源码错误回退不等于数据库迁移可降级，本版本没有引入不可逆升级迁移。

### 推荐：批量覆盖更新

拿到新版完整 ZIP 后：

```bash
python tools/backup.py --include-data --out ../logbench-before-update.zip
python tools/apply_update.py ../LogBench_R5_Server_v3.0.3_Floating_Details_Python39.zip
```

第二条的包名应替换为**实际新版本包**。工具先解包预检，再用 `.update-in-progress` 暂停监控，备份旧代码并批量原子替换应用文件，最后释放监控。仅接受可信代码包；预检需要执行包内 Python，不能把陌生 ZIP 当作安全数据文件。工具不覆盖 `data/`、`var/`、`config.json`、`run.py`，也不自动安装新版本的 `tools/` 或根目录快捷脚本；请从 ZIP 手动复制这些非监控文件。旧代码备份保存在 `.update-backups/`。

如果通过 SFTP 手工覆盖多个文件，先在部署根创建空文件 `.update-in-progress`，传输结束后删除它。否则传输中碰巧形成的“合法但不完整组合”仍可能通过基本预检。只改一个源文件也会触发更新。

**以下需要手动重启：** `run.py` 启动器自身、Python 环境、监听端口/Host/代理配置、systemd/容器托管方式。`rules/cpqpsgx-default.json` 只是首次初始化种子，覆盖它不会覆盖数据库中管理员已经维护的规则；现有规则通过管理页面修改。

可用 `python run.py --no-reload` 关闭监控。运行状态在管理员后台与 `var/runtime/current.json` 中；历史快照不会自动清理。长期频繁迭代后，应停服并备份，再清理不再需要的 `var/runtime/releases/` 与 `.update-backups/`，不要删除数据库和当前运行快照。

## 五、持久化与备份

服务端持久数据为 `var/logbench.sqlite3`、共享日志 `data/` 及其隐藏回收目录 `data/.logbench-trash/`。数据库内含稳定的命名空间密钥；删除/重建数据库会造成浏览器使用新的身份空间，旧缓存不自动跨身份迁移。

本机文件和个人设置属于 **固定 origin + 浏览器档案 + 当前 IP 身份命名空间**，应用无 TTL，不因正常刷新、关闭、代码升级而主动清空。换端口、主机、协议、浏览器档案或 IP，不是同一个工作区。浏览器可能拒绝持久存储、清理数据或受无痕策略限制，所以不能承诺“永不丢失”。本机存储入口会提示是否保存成功，并提供完整工作区导出/恢复。

从 R5 离线原型迁移时：先在旧页面导出“完整工作区备份”，再在新服务中恢复。**不自动读取旧的未隔离全局缓存**，避免把其他身份的文件暴露给新用户。原型内的规则可作为个人规则恢复，不会自动发布到服务器。

服务端备份：

```bash
# 数据库/身份/规则/绑定/审计 + 回收站，不含当前日志库正文
python tools/backup.py --out ../logbench-metadata.zip
# 再包含共享日志库正文
python tools/backup.py --include-data --out ../logbench-full.zip
```

SQLite 使用标准库在线备份 API，不直接复制正在写入的数据库文件。若要求数据库、文件删除状态和日志库为同一业务时间点，请先停止修改操作或停服再备份。备份 ZIP 含身份与日志敏感信息，应限制访问。服务端备份不包含任何用户浏览器的本机文件。

恢复前停服。备份中的 `state/logbench.sqlite3` 放回配置的 state_dir；`data/` 内容放回配置的 data_dir（含 `.logbench-trash/`）；按需恢复 `config.json`。把旧数据库/WAL/SHM先整体移出备份，不把旧 WAL 与恢复的数据库混用，再启动服务。

## 六、性能与已知边界

目录查询不读日志正文；文件表每页显示 200 条元数据。阅读每页 1,000/5,000/10,000/30,000/50,000 条，使用虚拟列表，不一次创建五万条 DOM。解析/规则/正则搜索在浏览器 Worker 中执行；每个服务器文件首次打开才下载，关闭后可释放阅读窗口。

当前沿用 R5 的 **单文件 64 MiB、打开的原文总量 128 MiB** 安全边界。总库可有更多文件，但一次全局筛选/对比仍受打开窗口限制，不会自动把几 GB 日志全部装入浏览器。64/128 MiB 是原文额度，不是浏览器内存峰值保证；解析对象、索引与对比时间轴另占内存。

多文件按原始时间比较，保留原始小数秒；不自动校正时区/设备时钟。完整高容量服务端时间索引、流式尾随、GB 级日志查询、账号/SSO强认证不在本版本中。已支持当前任务的真实数据服务，不再是合成后台；上述边界不要当作隐藏能力。
